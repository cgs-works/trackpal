# Immediate confirmed Tenant Deletion

A Tenant Admin may initiate irreversible Tenant Deletion without prior deactivation or Master approval. TrackPal executes deletion immediately after password reauthentication and a locale-aware destructive word (`ELIMINAR` / `DELETE`), rather than introducing a grace-period state that would require deferred jobs and a separate recovery channel. The Master keeps the existing lifecycle in the Master dashboard: deactivate first, then delete with the same password and destructive-word confirmation. Inactive Tenants cannot be opened in support context, so the self-service deletion action is not exposed there.

External cleanup is fail-closed and idempotent: TrackPal purges the latest R2 export and deletes the Evolution instance before committing the PostgreSQL deletion. Failure stops deletion and permits retry. Because these systems cannot share a transaction, a rare final database commit failure can leave the Tenant temporarily present after external cleanup; retrying the same operation completes deletion safely. Redis session cleanup is best-effort because its keys are ephemeral and cannot authorize a deleted Tenant. Tenant Deletion promises immediate removal from active systems; infrastructure backups and logs expire under their operational retention policies.
